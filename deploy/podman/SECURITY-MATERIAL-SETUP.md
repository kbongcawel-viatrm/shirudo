# Shirudo security material: step-by-step setup

This procedure prepares two separate identities on the operator host:

1. A self-signed TLS CA certificate and private key for the local Podman OCI registry.
2. A Shirudo ML-DSA-87 package-signing key and its DER X.509 certificate, generated by Shirudo itself.

Private keys remain on the operator host. Never commit them to GitHub, upload them to chat, mount them into application containers, or copy them to a target.

## 1. Prerequisites

Use a trusted Linux operator machine with OpenSSL 1.1.1 or newer, the Shirudo operator CLI, Podman and a compatible Compose provider. Ensure the operator account has a protected home directory and encrypted storage or an encrypted offline backup.

Check the CLI:

~~~bash
shirudo version
shirudo genkey --help
shirudo bpm key fingerprint --help
~~~

The signing-key generation must use Shirudo's own genkey command. The documented format is ML-DSA-87 PEM private key plus a self-signed DER X.509 certificate. Do not substitute a generic OpenSSL RSA or ECDSA key pair.

## 2. Generate both identities

From the repository root:

~~~bash
chmod +x deploy/podman/scripts/setup-security-material.sh
KEYS_DIR="$HOME/.config/shirudo/keys" \
REGISTRY_DIR="$PWD/deploy/podman/secrets/registry" \
REGISTRY_HOST=localhost \
REGISTRY_IP=127.0.0.1 \
./deploy/podman/scripts/setup-security-material.sh
~~~

The script refuses to overwrite existing material. It creates:

~~~text
deploy/podman/secrets/registry/
  server.crt       # Registry TLS CA certificate
  server.key       # Registry TLS private key, mode 0600

~/.config/shirudo/keys/
  signing_key.pem  # Shirudo ML-DSA-87 private key, mode 0600
  cert.der         # Shirudo X.509 signing certificate, DER, mode 0600
~~~

The registry certificate SAN defaults to DNS localhost and IP 127.0.0.1. These values are suitable only when clients connect using those exact names. If clients use another hostname or IP, set REGISTRY_HOST and REGISTRY_IP to the actual registry identity before generation. Do not disable TLS verification to work around a hostname mismatch.

The script prints the signing certificate's SHA-256 SPKI fingerprint. Record it separately through a trusted channel for later publisher verification.

## 3. Verify generated files

~~~bash
KEYS_DIR="$HOME/.config/shirudo/keys"
REGISTRY_DIR="$PWD/deploy/podman/secrets/registry"

test -s "$REGISTRY_DIR/server.crt"
test -s "$REGISTRY_DIR/server.key"
test -s "$KEYS_DIR/signing_key.pem"
test -s "$KEYS_DIR/cert.der"

stat -c '%a %n' "$REGISTRY_DIR/server.key" "$KEYS_DIR/signing_key.pem" "$KEYS_DIR/cert.der"
openssl x509 -in "$REGISTRY_DIR/server.crt" -noout -subject -issuer -dates -ext subjectAltName
openssl x509 -inform DER -in "$KEYS_DIR/cert.der" -noout -subject -issuer
shirudo bpm key fingerprint "$KEYS_DIR/cert.der"
~~~

The Shirudo signing helper requires signing_key.pem to be a regular file with mode exactly 0600. Do not display or transmit either private key.

## 4. Configure the operator shell

From the repository root:

~~~bash
export KEYS_DIR="$HOME/.config/shirudo/keys"
export CA_CERT="$PWD/deploy/podman/secrets/registry/server.crt"
export REGISTRY="oci://127.0.0.1:15444/shirudo"

./deploy/podman/scripts/shirudo-operator.sh version
./deploy/podman/scripts/shirudo-operator.sh keys-check
~~~

CA_CERT is the public registry CA certificate. It is not the registry private key and not the Shirudo signing certificate. For Shirudo OCI operations, use:

~~~bash
export BPM_OCI_CA_FILE="$CA_CERT"
~~~

Keep registry credentials separate. Do not put passwords in shell history or repository files.

## 5. Start the Podman support stack

~~~bash
cd deploy/podman
cp .env.example .env
podman compose --env-file .env config
podman compose --env-file .env up -d
podman compose ps
~~~

The registry service mounts server.crt and server.key. Ports bind to loopback by default. Do not expose the unauthenticated lab registry publicly without authentication, network controls and a certificate for its actual DNS identity.

## 6. Build and publish a reviewed Shirudo package

Only package a valid, reviewed Beefile and supported upatch artifacts. The Python, Node.js, TypeScript, Vite, C, Go and Rust images in this project are scan fixtures; scanning them does not create Shirudo upatches.

Build and inspect using the documented CLI:

~~~bash
shirudo bpm build ./path/to/package --version 1.0.0 --keys-dir "$KEYS_DIR"
shirudo bpm info ./package-1.0.0.bee
shirudo bpm key fingerprint ./package-1.0.0.bee
~~~

Publish the resulting package using the documented package path and explicit key directory. The first package in a namespace may require --new-index:

~~~bash
BPM_OCI_CA_FILE="$CA_CERT" \
shirudo bpm push ./package-1.0.0.bee oci://registry-host/namespace --keys-dir "$KEYS_DIR" --new-index
~~~

Confirm the exact destination and flags with shirudo bpm push --help for the installed version. Do not rely on provisional argument ordering in older helper scripts.

## 7. Verify the publisher before installation

Obtain the expected SHA-256 SPKI fingerprint independently through a trusted channel. Compare it with:

~~~bash
shirudo bpm key fingerprint oci://registry-host/namespace/package:version
~~~

The registry fingerprint must match the independently recorded value exactly. Enroll the signer and install only according to the target's provisioning mode and trust policy.

Targets using a signed config image manage trusted BPF signers through that signed configuration and a planned reboot. Local bpm key add is not permitted in config-image mode. Follow Shirudo's key-management documentation; do not blindly run a generic install command on a production target.

## 8. Backup and rotation

- Keep signing_key.pem in a protected operator-only location; maintain an encrypted offline backup.
- Back up cert.der alongside its matching private key.
- Record the SPKI fingerprint separately from the key files.
- Never run shirudo genkey --force over the active key. Rotation requires enrolling/vouching for the replacement certificate before switching signers.
- Registry TLS material can be rotated independently from the Shirudo package-signing identity.
- If a private key may be compromised, stop signing with it and follow Shirudo's signer revocation and target keyring recovery procedure.

## 9. Git hygiene

The generated paths must remain ignored:

- deploy/podman/secrets/
- ~/.config/shirudo/keys/

Check before committing:

~~~bash
git status --short
git check-ignore -v deploy/podman/secrets/registry/server.key
~~~

Never add generated private key files to a commit, issue, pull request, chat, or container image.

## Validation boundary

This change adds the local generation script and documentation; it does not generate or commit private keys. Run the script on the operator host where Shirudo is installed. Podman, registry TLS connectivity, package signing and target installation still require validation in the real deployment environment.
